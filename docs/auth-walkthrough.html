How “Login with Railway” works

Console doesn't have its own accounts or passwords. Railway signs the user in, and the user decides which Railway projects Console may manage. Console gets a token it can use to call Railway's API for that user, and keeps the token in an encrypted cookie that only the server can read.

This page walks through that one sentence slowly. Click, drag, and break things along the way.

🧑‍💻

Browser

The user and their browser. It follows redirects and stores cookies, but we treat it as a place where secrets must not live.

🖥️

Console server

Our TanStack Start app (localhost:3000). It holds the secrets and is the only party that ever sees Railway tokens.

🚂

Railway

Two roles: the authorization server (login and consent screen, issues tokens) and the GraphQL API (accepts those tokens).

Chapter 5 · Deep dive

PKCE: proving you're the one who asked

The authorization code travels through the URL bar, so it can leak through browser history, logs, or extensions. PKCE (“pixy”, Proof Key for Code Exchange) ties the code to a secret that only Console holds. A leaked code is useless without it.

Lab: a real verifier and challenge, computed in your browser

Same algorithm as arctic's generateCodeVerifier() and CodeChallengeMethod.S256: 32 random bytes, then base64url(SHA-256(verifier)).

🔒 code_verifier: stays with Console

Kept in the httpOnly railway_oauth_verifier cookie and only sent to Railway in step ⑪, over the back channel.

🌐 code_challenge: public, goes in the URL

Sent in step ⑥. Railway stores it next to the code it's about to issue.

SHA-256 is one-way, so knowing the challenge doesn't help you work out the verifier. (Console also sends its client secret when exchanging the code, which is a second lock. PKCE is still recommended for every client, and OAuth 2.1 requires it.)

Chapter 6 · Deep dive

The session cookie: a locked box only the server can open

After login, Console needs to remember the user's Railway tokens. Most apps keep a sessions table in a database and put a random ID in the cookie. This code skips the database: it puts the tokens in the cookie, encrypted, so the browser carries a box it can't open.

Option A: database session (not used here)

Cookie: sid=8f3a…, a random pointer.
Server: looks up row 8f3a… → tokens.

Needs a database. You can list sessions and revoke them on the server.

Option B: encrypted cookie (this code)

Cookie: railway_session=eyJhbGciOiJkaXIi…, the tokens themselves, encrypted.
Server: decrypts it with SESSION_SECRET.

No database. Every request carries its own state. Revoking a single session is harder (see Trade-offs).

Lab: encrypt a session exactly like writeSession()

JWE · alg dir · enc A256GCM · real WebCrypto
Press Encrypt…
■ header (readable) ■ key (empty for “dir”) ■ IV (random each time) ■ ciphertext ■ auth tag
The server hasn't read anything yet.

Two properties matter here. Confidentiality: without the secret, nobody can read the Railway tokens inside. Integrity: AES-GCM's auth tag means any edit, even one bit, makes decryption fail, so nobody can forge or modify a session. Try encrypting the same payload twice: the output changes every time because the IV is random. 

async function encryptionKey() {
  // SHA-256 squeezes any-length SESSION_SECRET into exactly the 32 bytes AES-256 needs
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(env.SESSION_SECRET));
  return new Uint8Array(digest);
}

export async function readSession() {
  return decryptSession(getCookie(SESSION_COOKIE));
}

async function decryptSession(token) {
  if (!token) return null;
  try {
    const { payload } = await jwtDecrypt(token, await encryptionKey());
    return Session.parse(payload.session);   // zod: also rejects old/unknown shapes
  } catch {
    return null;                              // tampered, expired, wrong secret → "signed out"
  }
}

Chapter 8 · Deep dive

The token clock: why there are two tokens

The access token is what Railway's API accepts, and it expires after an hour so a leaked one doesn't stay useful for long. The refresh token lasts longer and can only be used at the token endpoint, together with the client secret, to get a new access token. getFreshSession() runs on every page load (through getRailway()) and handles the switch.

// server/railway/backend.ts
export async function getRailway() {
  const session = await getFreshSession();                     // decrypt cookie, refresh if needed
  if (!session) return null;
  const railway = createRailwayClient(session.accessToken);
  return readBackend() === "mock" ? createMockRailwayClient(mockRailway(), railway) : railway;
}

// domains/project/viewer.ts
export async function fetchViewer(railway: RailwayClient) {
  const { me, externalWorkspaces } = await railway(ViewerQuery);
  return { user: me, workspaces: externalWorkspaces };   // ← the only Railway data that crosses the wall
}

Chapter 11

      
Trade-offs and things to know

      

        None of these are bugs today. They're consequences of choices in the design that are worth
        knowing before you build on top of it.
      

      

        

          
🚪 Logout is local

          

            “Log out” deletes the cookie in this browser. The Railway tokens aren't
            revoked, though only the server ever held them. With no session table, there's also no
            “sign out everywhere” except rotating SESSION_SECRET, which signs out
            everyone. arctic has a revokeToken() if you want to revoke at
            Railway on logout.
          

        

        

          
🏁 Two tabs refreshing at once

          

            If two requests arrive in the last minute before expiry, both will refresh. This can
            even happen within one page load: the root loader (getShell in
            __root.tsx) and then each project the home loader prefetches go through
            getRailway() → getFreshSession(), and the prefetches run in
            parallel. They all read the cookie the request arrived with, so none of them sees a
            token another one just refreshed. If Railway rotates refresh tokens and rejects reuse of
            an old one, the slower calls fail and those parts of the render show signed-out or
            unavailable. The cookie written by the other call survives, so the next load is fine.
          

        

        

          
🔑 SESSION_SECRET must be random

          

            The key is a single SHA-256 of the secret, not a slow password hash. That's fine for a
            long random string (openssl rand -base64 32) and weak for a memorable
            phrase. The zod schema only enforces length ≥ 32.
          

        

        

          
📏 Cookies max out around 4 KB

          

            Browsers cap each cookie at about 4 KB. Two tokens plus JWE overhead fits easily today.
            If you later add the ID token or user profile to the session, watch the size.
          

        

        

          
🌍 APP_URL must match exactly

          

            The redirect URI is built from APP_URL + "/auth/callback" and has to match
            what's registered on the Railway OAuth app, character for character. Each deploy URL
            (preview, prod) needs its own entry.
          

        

        

          
♻️ Failed refresh leaves the stale cookie

          

            When a refresh fails, getFreshSession() returns null but
            doesn't clear the cookie, so each page load retries the refresh until the user logs in
            again. That's harmless, just one wasted request per load.
