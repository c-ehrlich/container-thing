How the project page stays live

You open a project in Console and see its services: running, stopped, deploying. Someone else runs railway up from their laptop, and a second later your page shows it, without a reload. This page explains how, from “what is a GraphQL subscription” up to the specific choices in the code.

Everything is clickable: step through the message flows, poke at the protocol, and break the live connection on purpose to see what the app does.

🧑‍💻

Browser

React components, plus a TanStack Query cache that holds the data they show, and one WebSocket for live updates.

🖥️

Console server

TanStack Start. Server functions for reads and writes, and a small WebSocket relay at /api/live. Only this box ever holds the Railway token.

🚂

Railway

A GraphQL API: plain HTTP for questions and commands, WebSockets for “tell me when something changes.”

Reading The page asks the server for the project (a query). TanStack Query keeps the answer in a cache entry under the key projectScope(projectId) (that is, ["project", projectId]), and every screen reads from there.
Writing Start/Stop buttons send a mutation through a server function. When it succeeds, the page doesn't edit the cache by hand. It marks the cache entry as out of date (“invalidates” it), which triggers a fresh read.
Staying live The browser holds a WebSocket to our relay, which holds WebSockets to Railway. Railway pushes subscription events. Each event is treated as a signal (“something changed”), never as data. The response is always the same: invalidate and read again.
Chapter 1

GraphQL's three verbs

Railway's API is GraphQL. Every request you send it is one of three kinds of operation. The first two are ordinary request/response. The third is different: you ask once, and answers keep coming.

Why the third one needs a different pipe

A normal HTTP request is a phone call where you ask one question, get one answer, and hang up. A subscription needs the line to stay open so Railway can speak first, any time. That's a WebSocket: a connection that starts as an HTTP request, then gets “upgraded” into a two-way channel that stays open as long as both sides want. Chapters 5 and 6 open one up.

Chapter 4

Queries, server functions, and the cache

Three tools work together here. Server functions let browser code call code that runs on the server. TanStack Query remembers the results. TanStack Router loads data before a page renders, both on the server and in the browser.

1. Describe the query once

projectQuery(projectId) bundles two things: a key (the name of the cache entry) and a function that fetches the data. The loader, the project page, the overview, the chat widgets, and the live watcher all pass the same object around, so they all point at the same cache entry. The key starts with projectScope(projectId), so invalidating that prefix refreshes every entry about the project at once. 

export const projectScope = (projectId: string) => ["project", projectId] as const;

export const projectQuery = (projectId: string) =>
  queryOptions({
    queryKey: [...projectScope(projectId), "project"],
    queryFn: () => getProjectFn({ data: { projectId } }),
    staleTime: 30_000,
  });

2. Load before render, read during render

The route's loader runs before the page renders and fills the cache. The component then uses useSuspenseQuery, which reads that entry and keeps the component subscribed to it, so it re-renders whenever the entry changes.

3. A server function hides the token

getProjectFn is declared with createServerFn. Its body only ever runs on the server. When the browser calls it, TanStack Start sends an HTTP request to the server, runs the body there, and returns the result as JSON. Before the body runs, the requireRailway middleware reads the encrypted session cookie, refreshes the token if needed, and hands the handler a ready-made Railway client (or the mock, if this browser picked it in the sidebar). 

export const requireRailway = createMiddleware({ type: "function" }).server(async ({ next }) => {
  const railway = await getRailway();   // fresh session + real or mock backend
  if (!railway) { setResponseStatus(401); throw new Error("Not signed in to Railway"); }
  return next({ context: { railway } });
});

const getProjectFn = createServerFn({ method: "GET" })

Why two observers watch the same entry

ProjectPage reads the data with useSuspenseQuery. keepEnvironmentLive (in domains/live/use-live.ts) isn't a React hook. It runs outside React, and creates its own QueryObserver on the same key. That is what useQuery uses under the hood. The observer does three jobs: it keeps the entry active, so invalidating it refetches. It tells the watcher which deploys are in flight. And it carries an option, refetchInterval, which turns polling on and off. Options like that belong to each observer, while the data lives once in the cache. Both observers share one entry, and one fetch updates both.

Chapter 5

Why not just poll?

The simplest way to stay up to date is to ask again every N seconds. It works, and this app still does it as a fallback. The problem is the trade-off: poll often and you burn requests; poll rarely and the page is out of date.

Chapter 6

Subscriptions over a WebSocket

A WebSocket is just a pipe that carries messages both ways. To run GraphQL subscriptions over it, both ends need to agree on the message format. That agreement is a protocol called graphql-transport-ws, and graphql-ws is the library that speaks it. This app speaks it twice: browser ⇄ relay, and relay ⇄ Railway.

The whole protocol, roughly
connection_init“Hi, here are my credentials.” First message after the socket opens. connection_ack“OK, you're in.” subscribe {id}Start a subscription. The client invents the id, and many subscriptions share one socket. next {id}One event for subscription id. Arrives whenever the server feels like it. error {id}That subscription failed and is over. complete {id}Either side: “subscription id is done.” The client sends it to unsubscribe. ping / pongKeep-alive. Either side can ping.
Our client, in one call
const client: Client = createClient({

Chapter 7

The relay: why the browser doesn't talk to Railway

Railway's WebSocket wants the access token in connection_init. Giving it to browser JavaScript would undo the whole point of the server boundary from part 1. So the browser connects to our server, which authenticates it with the session cookie and opens its own connection to Railway with the token.

Chapter 8

Pushes are signals, not data

This is the key idea of the design. When an event arrives, the app doesn't try to patch the page with what the event says. It asks the server for the full, current project again. There is one writer for the cache (the refetch), so the page can't drift out of sync because of a missed, duplicated, or out-of-order event.

canvasInvalidation(environmentId)

An internal, undocumented Railway subscription that may change without notice. It's what Railway's own dashboard uses. It sends only an id, a hash of the environment's state, and re-sends it every 2 → 4 → 8 s. When the hash changes, something changed, whoever changed it.

deployment(id)

Public API. One subscription per deploy in flight on screen (deploying or stopping). It pushes SUCCESS, REMOVING, and REMOVED (measured: not the in-between states). It's a second, independent signal for the deploys you can already see going.

Things to notice in the lab

The first hash always refetches.

lastHash starts out undefined, so the first push counts as new. That covers anything that changed between the server render and the moment the subscription started.

New deployments get subscribed after a refetch.

The deploys to subscribe to come from the data on screen. Start the worker: canvasInvalidation notices first, the refetch reveals a new deployment ID, and only then does a deployment(id) subscription start for it.

Debounce turns a burst into one request.

Each event restarts a 250 ms timer, and the refetch happens once the events stop. Without it, every event would call invalidateQueries, which cancels the fetch already in flight and starts a new one (red bars).

Silence is a failure too.

A watchdog checks every 5 s. After 30 s without any hash (even a repeated one), the watch switches to polling. Pushes resuming switch it back. Use 4× speed to watch it happen.

Chapter 9

When it breaks

Live connections fail in more ways than requests do: they can drop, go quiet, or be ended by the other side. The rule here is simple. A watch counts as live only when both the socket is connected and canvasInvalidation is healthy. Otherwise the project's query polls every 30 s, so it's never stale for long. (This mode is internal: it only switches polling on and off, and the UI doesn't show it.)

Chapter 10

Small stores outside React

Three pieces of state live outside React state: the connection status (inside the one relay transport, for the whole app), the environments being watched (a counted map in use-live.ts), and a shared one-second clock. The engine reads the connection through its LiveTransport: connection() and onConnectionChange(). React only reads the clock, with useSyncExternalStore, which takes three functions. 

/** A clock shared by every `Elapsed`, ticking once a second while any is mounted. */
let clockNow = Date.now();
const clockListeners = new Set<() => void>();

function useNow(): number | null {
  return useSyncExternalStore(
    subscribeToClock,   // add a listener (starts the 1 s interval)
    () => clockNow,     // read it now
    () => null,         // what the server renders
  );
}

subscribe: “call me when it changes.” getSnapshot: “what is it now?” getServerSnapshot: “what should the server-rendered HTML say?”

The watches need no React store at all. The first watcher of an environment starts keepEnvironmentLive and the last one to unmount stops it (retainWatch). So the project page and a chat widget showing the same environment share one set of subscriptions.

The third function matters for hydration. The clock's server snapshot is null, so Elapsed renders nothing on the server. The server's clock and the browser's clock would disagree, and React would complain about mismatched HTML. Effects don't run on the server either, so nothing is watched there: the watch starts once the page hydrates.
